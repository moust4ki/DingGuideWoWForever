# Ding — specification

Ding is a free leveling guide addon for **World of Warcraft: Forever**
(client 1.60.x, interface `16001`). It shows the current step and an arrow to the next
objective, and moves on by itself when the player accepts, completes or turns in a quest.

Project goals:

1. **An engine independent of the guides.** Anyone can write a guide, in Ding or in a
   separate addon, without touching the engine.
2. **Guides optimized for XP per hour**, generated by an out-of-game optimizer and then
   adjusted by hand.
3. **The Claude Design interface** (`docs/UI-handoff.md`), unobtrusive (adjustable opacity)
   and fully usable with a gamepad, with its own arrow (TomTom is not needed).

---

## 1. Architecture

```
               out of game                                  in game
 ┌──────────────────────────────────────┐   ┌────────────────────────────────────┐
 │ QuestieDB (merged Forever export)    │   │ Ding/DB (built from that export)   │
 │            │                         │   │            │                       │
 │            ▼                         │   │            ▼                       │
 │ tools/ : extraction ─► optimizer ────┼──►│ Ding/Guides/*.lua ─► Ding engine   │
 │            ▲                         │   │                         │          │
 │            └── time measurements ◄───┼───┤ SavedVariables (DingDB.timings)    │
 └──────────────────────────────────────┘   └────────────────────────────────────┘
```

| Component | Role |
| --- | --- |
| `Ding/Core` | Namespace, API compatibility, data access, registry, step machine, timing |
| `Ding/DB` | Ding's game database, generated by `tools/build_data.lua` from a QuestieDB release |
| `Ding/UI` | Step panel and arrow |
| `Ding/Guides` | Guides shipped with the addon |
| `tools/` | Out-of-game scripts: zone listing, guide validation, then the optimizer |

### Game data: Ding/DB, from Questie's database

Questie's database (published under the GNU GPL v3, kept up to date in **QuestieDB**) contains
Forever's quests, NPCs, objects and items, including the new ones as they are discovered.

- **In game**, Ding reads its own copy, `Ding/DB`, through `Core/Data.lua`: no other addon to
  install. `tools/build_data.lua` writes it from a QuestieDB release (the Forever export, its
  zone tables and its names in every language): only the fields Ding reads, spawns already by
  UiMapID, one file of names per language (loaded by that client only). Questie's credits are
  kept (`Ding/DB/CREDITS.md`). The QuestieDB addon is only read when `Ding/DB` is missing.
- **On each QuestieDB release**, `Ding/DB` is built again from it, and `db_parity_test` checks
  that Ding gets the same answers from both; CI uses the release named in `Ding/DB/DB.lua`.
- **Out of game**, the tools read the merged export produced by
  `tools/export-forever.lua` in the QuestieDB repository.
- The **guides** contain only quest IDs and the order of the steps: that is our work. Names,
  NPCs and coordinates come from the database at display time.

Getter semantics, the same for both sources (QuestieDB's `docs/api.md`):

- a missing numeric field is `0`, never `nil`;
- `startedBy`, `finishedBy` and `objectives` always return a table;
- spawns: `Ding/DB` stores them by **UiMapID** (`{ [map] = { x, y, x, y, ... } }`); QuestieDB
  groups them by **AreaID**, as percentages 0-100, and `Data` converts them with its zone table.

## 2. Guide format

A guide is a Lua file that calls `Ding.RegisterGuide`: it is a **section** of a **guide
pack**. Ding ships three: **Ding! - Leveling** (id `ding`, the default, the pack of the guides
that have no `pack`: each section is a stretch of the Leveling routes, a race start then
shared sections up to 60 over one or a few zones), **Ding! - Zones** (id `ding-zones`: one section per zone, the ids
of Ding's first guides) and **Ding! - Items** (id `ding-items`, category `items`: one section
per item worth getting off the leveling route, for both sides: the Cozy Sleeping Bag first). A third-party addon provides a pack by declaring
`## Dependencies: Ding`, then calling `Ding.RegisterGuidePack({ id, title, author, category })` before
its sections, which carry `pack = "<id>"`; like Ding, it must be released under GPL v3 (no
exception: everything built on Ding stays free). The author documentation is
[`docs/guide-packs.md`](guide-packs.md), with a tested example pack
(`examples/DingExamplePack`) and the validator `tools/check_guides.lua --addon <folder>`.

Registry rules: a pack id is unique (Ding's included); a section id is unique across all
packs (a pack cannot take another pack's id, but may re-register its own section); an
unknown `pack` is rejected; `next` may lead to a section of another pack (Ding's included).
A pack's `category` (`Ding.GUIDE_CATEGORIES`: "leveling", the default, "items", "reputations",
"professions", "class") groups it in the guide list, under a header that cannot be picked,
leveling first, empty categories left out; an unknown category is "leveling" (debug note,
warning of the validator). Picking a pack again takes up the section the character last
followed in it (`Ding.char.packGuide`) while it has quest work left at their level, else the
suggested one; the section itself resumes at its `Ding.char.lastStep`: an item guide and back
to the leveling route loses nothing.

```lua
Ding.RegisterGuide({
    id       = "nightelf-01-shadowglen",   -- unique, stable
    pack     = nil,                        -- pack (Ding.RegisterGuidePack); nil = Ding's own
    title    = "Shadowglen (1-6)",
    faction  = "Alliance",                 -- "Alliance" | "Horde" | nil (both)
    races    = { "NightElf" },             -- English client names (UnitRace, 2nd value); nil = all
    classes  = nil,                        -- e.g. { "HUNTER" }; nil = all
    minLevel = 1, maxLevel = 6,
    next     = "nightelf-02-dolanaar",     -- next guide, chained automatically; or one per
                                           -- faction: { Alliance = "...", Horde = "..." }
    steps    = { ... },
})
```

### Steps

A step groups one or more **actions**. It is done when all of its actions are done. The
actions of a step run in order: turn in, then accept, then complete.

| Key | Value | Done when |
| --- | --- | --- |
| `turnin` | id or list of ids | the quest is turned in |
| `accept` | id or list of ids | the quest is in the log (or already turned in) |
| `complete` | id or list of ids | the quest's objectives are met (or it is turned in) |
| `go` | `{ uiMapId, x, y }` (0-100) | the player is within `radius` meters (10 by default) |
| `level` | number | the player reaches that level (Ding shows the experience and kills left, and a monster to farm); `level = 12, xp = 4500` (plus that experience into level 12) or `level = 12.5` (that fraction of level 12's experience: `Grind:Into`, `Engine:LevelReached`) |
| `sethearth` | inn name | the hearthstone is bound (`HEARTHSTONE_BOUND` event) |
| `hearth` | `true` | the hearthstone is cast (`UNIT_SPELLCAST_SUCCEEDED`, spell 8690), or "Next" |
| `deathskip` | `true` (+ `text`) | the player died during the step and is alive again, or "Next" |
| `train` | `true` / text | a class trainer's window (not a profession's) opened during the step is closed, a spell is learned during the step (`LEARNED_SPELL_IN_TAB`, not at a profession trainer), or "Next"; behind the option "Class trainer steps" (`ui.trainerSteps`, on by default) |
| `fly` | `true` / text | a flight map opens or a new flight path is found (`ERR_NEWTAXIPATH`), or "Next"; behind the option "Flight path steps" (`ui.flightSteps`, on by default) |
| `vendor`, `repair` | `true` / text | a merchant's window opened during the step is closed, or "Next"; behind the option "Vendor and repair steps" (`ui.serviceSteps`, on by default) |
| `text` | text | manual validation ("Next" button) |

Goals without a quest (`Core/Goals.lua`, Phase 9), combined with the keys above (the step is
done when all of its parts are); a pair is `{ id, count }` (a list of pairs; one pair alone or
a bare id are read too):

| Key | Value | Done when |
| --- | --- | --- |
| `kill` | pairs `{ npcId, count }` | killed `count` times since the step began: `CHAT_MSG_COMBAT_XP_GAIN` read with the client's `COMBATLOG_XPGAIN_FIRSTPERSON` (`Compat.FormatPattern`, open-ended for the rested and group bonuses), the name matched to QuestieDB's; progress in `Ding.char.goals["<guide>#<step>"]` |
| `collect` | pairs `{ itemId, count }` | `GetItemCount` reaches the count |
| `buy` | `{ itemId, count, vendorNpcId? }` list | `GetItemCount` reaches the count; the arrow on the vendor given, QuestieDB's `vendors` of the item, else the nearest vendor |
| `talk` | NPC id(s) | an NPC window opens (gossip, quest greeting / detail / progress / complete, merchant, trainer, flight map, bank, stable) with that NPC (`UnitGUID("npc")`'s creature id, else its name) |
| `gossip` | option index | `GOSSIP_CLOSED` after a `GOSSIP_SHOW` of the step; while open, a banner names the line (`C_GossipInfo.GetOptions`, else `GetGossipOptions`); never selected by Ding |
| `useitem` | item id(s) | its spell cast (`UNIT_SPELLCAST_SUCCEEDED` = `C_Item.GetItemSpell`), its count below the step's start, or the objectives of the step's `complete` quests advanced; offered on the item button |
| `object` | object id(s) | `LOOT_OPENED`, `GOSSIP_SHOW`, `QUEST_DETAIL` or `ITEM_TEXT_BEGIN` within 20 yards of one of its spawns (or `spots`) |
| `equip` | item id(s) | worn in any slot (`GetInventoryItemID`); offered on the item button |
| `destroy`, `bank` | item id(s) | none left in the bags (never done by Ding) |
| `unbank` | item id(s) | in the bags |
| `abandon` | quest id(s) | out of the log (never done by Ding) |
| `keep` | item id(s) | reminder only: `Ding.char.keep`, never sold as a grey item (`Core/Merchant.lua`) |
| `spots` | `{ uiMapId, x, y }` list | authored places for `kill`, `collect`, `object` (an area) instead of QuestieDB's spawns |

Each part is a line of the window (`action` = "goal", the kill / objective / use glyphs, a
counter `2/8`); a click (A) aims the arrow at that part; on a `useitem` or `equip` line A uses
the item button.

Common options:

| Key | Role |
| --- | --- |
| `note` | tip shown under the step |
| `optional` | the step can be passed without blocking what follows |
| `faction` | `"Alliance"` or `"Horde"`: the step only appears for that side (`UnitFactionGroup`), in a guide for both sides |
| `races`, `classes` | the step only appears for these races/classes |
| `radius` | arrival radius of a `go` step |
| `use` | item id or list of item ids to offer in the item button (the first one owned) |
| `sticky` | quest id or list: persistent objectives, see "Along the way" |
| `dungeon` | dungeon name: the step's quests are done inside it |
| `elite` | `true`: the step's quests are against elite monsters |
| `when` | conditions, all must hold (`Engine:ConditionsHold`): `done`, `notdone`, `log`, `notlog`, `ready` (quest ids), `item` (id or `{ id, count }`), `noitem`, `minlevel`, `maxlevel`; else the step does not apply (`Ding:StepApplies`), re-read on quest log, level and bag changes |
| `noauto` | quest id(s) AutoQuest never accepts (`Engine:NoAuto`); turned in as usual |
| `revive` | on a `deathskip` step, `{ uiMapId, x, y }`: as a ghost the arrow goes to that spirit healer ("Spirit healer", reached within 30 yards) instead of the corpse; `"corpse"` by default |
| `patrol` | `{ uiMapId, x, y }` list: the arrow's only point is the current one ("text · point 2 of 5"), the next once reached within `radius` (`Engine:PatrolPoint`, session state `Engine.patrol`); until the step's quests, goals and level are done, or "Next" when it has none |

**Steps behind an option** (Route tab, `Ding:StepApplies`): `sethearth` and `hearth`
need "Manage the hearthstone" (`ui.hearth`, on by default), `deathskip` "Death skips"
(`ui.deathSkip`), `dungeon` the choice for that dungeon (`ui.dungeonChoice[name]`, a row per
dungeon the active guide's pack names, `Engine:DungeonNames`) and by default "Dungeon quests"
(`ui.dungeons`, `Ding:DungeonWanted`), `elite` "Elite quests"
(`ui.elites`), all three off by default. A step whose option is off does not apply, like a
step for another race: Advance passes it, AutoQuest ignores its quests, "back to a skipped
step" never comes back to it. Turning an option on takes effect from the current step; the
steps passed before come back with "back to a skipped step". The window adds the step's tag
under it ("Dungeon: Gnomeregan", "Elite quest: better with a group.", how a death skip
works). The generator puts these keys on steps of their own, and `dungeon` / `elite` on
every step of the quest.

`next` keyed by faction (`{ Alliance = id, Horde = id }`): the Skyborne start is neutral
until the character picks a side around level 12-13; the engine chains to the entry of
`UnitFactionGroup("player")` (`Engine:NextGuide`), and a character with no side yet, or a
side missing from the table, finishes the guide.

Examples:

```lua
{ accept = { 456, 458 } },
{ complete = 456, note = "Nightsabers and boars around Aldrassil." },
{ turnin = 456, accept = 457 },
{ go = { 1438, 55.6, 59.8 }, text = "Head for Dolanaar" },
{ train = true, text = "Visit your class trainer." },
```

The engine generates the text itself ("Accept *The Woodland Protector* — Melithar Staghelm")
in the client's language, from QuestieDB. The guide does not need to spell out the names.

### Languages

The texts of a guide (`title`, `text`, `note`) are written **in English**, the default
language. Their translation lives in a separate file, `Ding/Locales/Guides/<locale>/<same
path as the guide>.lua`, loaded after the guides in `Ding.toc`:

```lua
Ding.RegisterGuideTranslation("frFR", "nightelf-01-shadowglen", {
    ["Head for Dolanaar"] = "Direction Dolanaar",
})
```

The key is the exact English text. A client in that language sees the translated text; any
other client, or a text with no translation, keeps the English. If the English text changes,
the translation no longer applies: `tools/check_guides.lua` reports untranslated texts
and orphaned translations.

Shipped languages, **one file per language**: French (frFR), German (deDE), Spanish
(esES, also loaded by a Latin American client, esMX), Brazilian Portuguese (ptBR),
Korean (koKR), Simplified Chinese (zhCN) and Traditional Chinese (zhTW). These are the
languages in which QuestieDB has quest, NPC and item names (no Italian: the Classic client
does not exist in that language).

- **Interface**: `Ding/Locales/enUS.lua` (reference) and one file per language,
  `Ding/Locales/<locale>.lua`, loaded only by a client in that language, with
  exactly the same keys and the same `%s`/`%d` in the same order.
- **Guides**: translations of the generated guides are not written by hand. Each
  language has its own dictionary, `tools/routes/locales/<locale>.lua` ([English sentence] =
  translation: zone names, route introductions, automatic notes, notes of the Shadowglen
  guide). `tools/translate_guides.lua` writes each guide's
  `Ding/Locales/Guides/<locale>/...` files and their lines in the TOC; a note that chains
  several sentences is translated sentence by sentence, and a title keeps its level range
  ("Westfall (11-16)": the dictionary names the zone). `tools/draft_guide.lua` does the
  same for the guides it generates.
- **Adding a language**: copy `Ding/Locales/frFR.lua` and `tools/routes/locales/frFR.lua`
  under the new code, translate them, add the code to `M.LOCALES` in `tools/guide_texts.lua`
  and the interface file to the TOC, then run `tools/translate_guides.lua`.
- **Font**: Noto Sans covers Latin and Cyrillic. A Korean or Chinese client keeps the
  game font (`UI.GAME_FONT` in `UI/Widgets.lua`).

### Guides as text (import and export)

A guide can also come as **text**, pasted in the game (public page:
[`docs/create-a-guide-with-ai.md`](create-a-guide-with-ai.md)): one Lua table literal, either
a guide `{ id?, title, category?, faction?, races?, classes?, minLevel?, maxLevel?, next?,
steps }` or a pack `{ pack = { id?, title, author?, category? }, guides = { ... } }`, with the
keys of section 2 above.

- **Reading** (`Core/GuideText.lua`): a reader written by hand, never `load`, `loadstring`,
  `setfenv` nor `RunScript`. It takes tables, texts (quoted or long brackets, `..` between
  texts), numbers, `true` / `false` / `nil` and comments; any other word (a function, a call,
  a variable) is refused. Limits: 300 KB, tables 10 deep, 100,000 values. A code fence
  (```` ```lua ````) around the table, as chat AIs write it, is read through.
- **Checks** (`Core/Import.lua`): only the keys of the format (a whitelist per guide, pack,
  step and `when`), each with its kind of value; the registry's rules (lists of ids, `go`
  as three numbers); QuestieDB: quests, NPCs and objects exist (an NPC or an object is only
  a warning when the step has `spots` or `go`), items (a warning), the quests taken are open
  to the step's races (its `races`, else the guide's, else its faction's), the guide's races
  are on its side; coordinates within 0-100 on a map the client knows; levels, text lengths
  (1,000), steps (1,000 per guide), guides (50). Errors block the import, warnings do not;
  each message is localized and says the line, the guide and the step.
- **Ids**: kept unless missing or taken by a pack of an addon or Ding's (or a guide of
  another pack): then `user-<id>` (`user-<title>` when missing), and `next` follows a
  renamed guide. Importing the same id again replaces the imported guide.
- **Storage**: `DingDB.imported[packId] = { pack, guides, at }`, account-wide. At login, once
  every addon has registered its packs and before the engine starts, each entry becomes a
  pack (`pack.imported = true`, its category) with its guides; an addon that took the id
  since moves the import to a `user-` id. A guide imported alone is a pack of the same id.
  Deleting it (`Ding.UnregisterGuidePack`) sends a character on it back to the pack it was
  on before (`Ding.char.prevPack`, its section and step), else to Ding's guide.
- **Export** (`Import:Export(id, compact)`): a pack, or a guide (the active one by default),
  written back with the same keys in a fixed order (a lone id written bare), one step per
  line; `compact`: one line, `|` written `\124`. A pack of one guide of its own id comes
  back as that guide. What is exported reads back without error, and exports the same.
- **Window** (`UI/ImportWindow.lua`, `/ding import`, `/ding export [id]`, the Guide tab's
  page **Guides as text**): the text in a scrolling box, the report in a second box (plain
  text, to copy back to the AI: "Error: Step 3: ..."), buttons. Gamepad: D-pad left / right
  between the buttons, A, Y selects the text or the report for Ctrl+C, B closes; temporary
  bindings, closed in combat. Mouse: the buttons, Esc. Opened from the settings, closing it
  comes back to the page. The window never takes the keyboard from a box that is not Ding's
  (the game's chat, which still has it while `/ding export` runs from it, and keeps it with
  the gamepad interface): the text takes it once the keyboard is free, the status line says
  so meanwhile.

## 3. Engine

### Progression

- The engine **automatically skips the steps already done**: when a character is picked up
  partway through, the guide realigns itself.
- **Resuming**: for 10 s after a guide is loaded (login, guide change, "restart"), a manual
  step (`go`, `train`, `fly`…) counts as done if a quest further on in the guide is already
  **turned in**. Quest data that arrives after login therefore still realigns the guide. A
  quest that is only accepted further on is not enough (it may have been picked up early).
  After that, a manual step is passed only by "Next" or by progress in the next 5 steps.
- **Guide choice** for a character Ding does not know yet, among the compatible sections of
  Ding's Leveling pack (its Zones pack when Leveling has none for the character), or of the
  chosen pack (see below), in this order: the first guide started and
  not finished (unless the character is past its maximum level); otherwise the first guide
  not started that covers the character's level; otherwise the last guide not started below
  that level. A guide counts as "started" only if one of its quests was accepted or turned in
  (a quest out of reach does not count).
- The player can switch guides at any time with the two drop-down lists of the Guide tab:
  **the guide** (Ding's three "built in" packs, Leveling, Zones then Items, then the installed packs
  by title, with their author and the levels they cover for the character; grayed out if it
  has nothing for them), then
  **the section** (only those of the chosen pack, including those for another race or class,
  grayed out). Choosing a pack loads its section for the character (same rule as above,
  otherwise its first section) and resumes it where the player is; choosing the active pack
  again changes nothing.
- The pack is remembered per character (`Ding.char.pack`). At login, if the remembered
  section is gone (pack updated), a section of that pack is offered; if the pack is gone
  (addon disabled), one from Ding's pack.
- It listens to `QUEST_ACCEPTED` (a single `questID` argument on Forever), `QUEST_TURNED_IN`,
  `QUEST_LOG_UPDATE`, `QUEST_REMOVED`, `PLAYER_LEVEL_UP`, `HEARTHSTONE_BOUND`.
- A turned-in quest is remembered immediately, because `IsQuestFlaggedCompleted` can answer
  with a slight delay.
- A quest whose required level is not reached yet is flagged ("level 3 required") without
  blocking the rest of the guide.
- If a step must complete or turn in a quest missing from the log (skipped for its level,
  abandoned…), Ding first shows "Accept …" and the arrow points to the quest giver.
- **Catching up on prerequisite quests**: a guide quest that cannot be accepted yet because
  an earlier quest in its chain was never turned in (`preQuestSingle`: any one of the quests
  is enough, `preQuestGroup`: all of them, according to QuestieDB) first shows what is left to
  do on the first missing link (accept, complete or turn in, "before …"), and the blocked
  quest in red. The arrow and automatic accepting follow that link. The quests of the step
  itself and those closed to the player's race or class do not count.
- **Gray quests** (setting, off by default): a quest that is gray for the player's level
  (the client's `GetQuestGreenRange`, otherwise the Classic formula), missing from the log and
  not a prerequisite of any quest in the guide, is skipped and never accepted automatically.
  Only on a leveling route: a guide of a pack of another category (items, reputations,
  professions, class; `Engine:KeepsGrey(guide)`) is followed for its reward and keeps them.
- **Skip reason**: under the current step, the panel says why the guide just passed steps
  without the player: "Skipped: … (gray quest)", "For later: … (level N required)"; two lines
  at most, then "and N more".
- An optional step is passed as soon as a later step makes progress, or right away if its
  quest was never accepted (starting item never dropped).
- After "Previous", the engine stays on the displayed step until "Next".
- **Skipping a step** (binding, right click on "Next", `/ding skip`): goes to the next step
  to do without validating this one, which is not timed. **Going back to a skipped step**
  (binding, right click on "Previous", `/ding back`) brings back the nearest step not done
  before the current step; once it is done, the guide moves forward again. Like any manual
  step, a skipped manual step counts as done as soon as a later step makes progress.
- **Resume where I am** (settings, guide list, `/ding guide`, first guide): the player's
  place is the last step where they turned in a quest, provided they have worked on (turned in
  or in the log) at least half of the quest steps up to there: a quest done early does not
  send them too far. The guide then starts over from the beginning: it passes what is done and
  what the player left behind, but **stops on any quest from the guide's past that is still
  in the log and remains to be completed or turned in** (a quest ready to turn in counts:
  Yendi's feedback, "Filthy Paws" skipped); a step whose log quests are only accepted does not
  stop it. Then it carries on to the player's place. The steps left behind remain reachable
  through "back to a skipped step". A section picked again (guide list, another pack and
  back) is taken up at least to the step the character was on in it (`Ding.char.lastStep`,
  or where a resume still in progress was going), so the steps the game cannot check later
  (a trip, a trainer, the inn, a step behind an option turned on since, a goal whose items
  are spent) are not asked again; "Take this guide up where I am" forgets it and starts from
  the quests alone. A `sethearth` step whose bind happened during the step stays done while
  the hearthstone is bound there (`Ding.char.hearthInn`: the client's own name of the inn
  then, so the language does not matter), also after "Take this guide up where I am".
- **Login**: the quest log arrives a moment after login. The engine places the player only
  once the log has been received (first `QUEST_LOG_UPDATE`, 5 s at most): without the log, a
  resume would believe every quest is missing and would skip the ones to turn in.
- **Updated guide**: a new version of Ding can regenerate a guide and move its steps.
  `Ding.char.guideSig` keeps the signature of the active guide (its quest actions and its
  level milestones, in order); if it changed at login, the guide is resumed where the player
  is instead of staying on a step number that is now wrong.
- **Trips with nothing left at the end**: a step that only takes the player somewhere (`go`,
  `fly`, `hearth`, nothing else) is passed as soon as the next step for the player is already
  done by the game's own state (its quests turned in, accepted or ready, its level reached),
  or is itself such a trip. A manual step next (class trainer, inn) keeps the trip.
- At the end of a guide, the engine chains to `next` if it exists.

### Automatic accept and turn-in (`Core/AutoQuest.lua`)

When the player talks to an NPC (gossip, greeting or quest windows), Ding accepts and turns
in **only the guide's quests**: those of the current step and the following ones, 5 steps at
most, stopping after a step that changes location (`go`, `fly`, `hearth`). Steps for another
race or class are ignored. A quest to complete or turn in that is missing from the log is
accepted again from its giver.

- **Along the way** (Yendi's feedback, Captain Rugelfuss): a quest the guide accepts further
  on is accepted if the NPC offers it, it is not above the player's level and the log holds
  fewer than 15 quests. It is recorded in `Ding.char.early`: a quest accepted early says
  nothing about the player's place and never passes a manual step (travel, class trainer),
  nor does it count for resuming; except a trip whose next step it completes: nothing is
  left at the end of that trip. Turn-ins stay at their step.
- **Above the player's level**: the routes respect "never above the player's level" for a
  simulated player. In game, a player who has fallen behind (skipped quests, deaths) sees
  such a quest **in orange with its level** ("· Level 16", on its line and under its
  objectives) and carries on: it is accepted like the others. Holding it back until the right
  level (v1.1.0) forced too much grinding (Yendi's feedback). Only the quests accepted along
  the way, ahead of the guide, still wait for the player's level.

- Turn in first, then accept; one quest per conversation (the client closes the window).
- A quest whose objectives are not met is never selected.
- The reward is taken only if there is no choice (or a single item); with several, see
  "Quest rewards" below.
- Two settings (Guide tab, on by default); holding Shift (LT on the gamepad) suspends
  everything.
- A selection that has no effect is retried only after 2 s (no loop on `GOSSIP_SHOW`).

### Choosing the destination point

| Current action | Candidate points |
| --- | --- |
| turn in | NPC or object that ends the quest |
| accept | NPC or object that starts the quest; for a quest started by an item, the monsters or objects that drop it |
| complete | spawns of the monsters, objects and item sources of the objectives **not met yet** (matched by objective name) |
| `go` | the given point |

The candidates of all the step's unfinished actions are offered together (turn-ins of ready
quests, quest givers, objective targets): among them, the arrow points to **the one closest to
the player** (real distance in yards, computed in world coordinates), chosen again every
second. Turn-ins still waiting on their objectives come only when nothing else is left, then
the step's `go` point.

### Travel (`Core/Travel.lua`)

Yendi's feedback: the arrow went in a straight line, whatever the distance. The arrow's
target (the nearest candidate) goes through a travel planner, the fastest way in seconds:

- **Legs**: walking (7 yards per second, 11 from level 40, 1.2 times the straight line), the
  **flight paths the character knows** (30 yards per second, 1.25 times the straight line, plus
  15 s to take off; between two known flight masters of the same continent open to the
  player's side), **boats, zeppelins and the tram** (crossing plus half a round trip of
  waiting), and the **hearthstone** from where the player stands to the inn (30 s, plus its
  cooldown). Each change of transport must save 20 s. Dijkstra over the player, the target,
  the known flight masters, the docks and the inn.
- **Flight masters never seen** (of the player's side): talking to one learns its path, so a
  flight may start there (never end there), 60 s slower for the doubt. The arrow then says
  "Try to fly to Lakeshire, Redridge".
- **Measured flights**: each flight taken is timed from `TakeTaxiNode` to the landing
  (`PLAYER_CONTROL_GAINED`); between 10 s and 30 minutes, it joins the average of that route
  (`DingDB.flightTimes["<from npc>:<to npc>"] = { seconds, count }`, at most 20 counted, account
  wide), which replaces the estimate from then on.
- **Teleports**, hearthstones of their own from where the player stands (30 s plus the spell's
  cooldown): the mage's cities of the player's side when the spell is known and a Rune of
  Teleportation is in the bags, the druid's Moonglade. Each lands where a QuestieDB NPC of the
  city stands. The arrow keeps the target with "Teleport to Stormwind City" and the item button
  casts the spell (`type` "spell", out of combat like any attribute).
- **Dangerous zones**: a walk is sampled every 400 yards (at most 6 looks, the zone under each
  cached per 300-yard cell); the share of looks in a zone more than 4 levels above the player
  (Classic zone levels, `Travel.ZONE_LEVELS`) makes the walk up to 2.5 times as long, so a flight
  or a boat around wins sooner.
- **Itinerary**: when the plan takes anything but a walk, the window writes it under the step,
  "Route: walk 1:20, fly 6:30 to Redridge Mountains, walk 0:40 (8:30 in all)"
  (`Travel:Itinerary(Travel.plan)`): each leg that is not a walk names the zone it leads to.
- **A continent never seen**: no flight map opened there yet (`Ding.char.taxiSeen[continent]`,
  set on `TAXIMAP_OPENED`; a flight path known there counts too) and a flight master of the
  player's side within 400 yards: a row "New continent: talk to … (flight master) to learn its
  flight paths" under the step (not on a `fly` step); a click (A in focus mode) leads there.
- **Taking the flight automatically** ("Take the flight automatically", Automation tab, Flights block,
  **off by default**, Yendi's decision): when the flight map
  opens and the plan flies the player to a node of that map they can reach, out of combat and
  without Shift (LT) held, Ding takes that flight (`TakeTaxiNode(index)` through
  `Compat.TakeTaxi`: the only call of the taxi API Ding makes, allowed by name in `taint_test`;
  the game's flight map frame is never touched), after `Dismount()` when mounted, and says
  "Flying to …" in the chat. Off, or anything else: only the highlight of the destination on
  the flight map.
- **Data**: flight masters from QuestieDB (`npcFlags` bit 8, `friendlyToFaction`), zeppelin
  towers and the Booty Bay - Ratchet boat where their masters stand in QuestieDB, the tram
  where QuestieDB's dungeon table enters it (Forever coordinates); only the Alliance boats
  (Menethil - Auberdine, Menethil - Theramore, Auberdine - Rut'theran), with no NPC on their
  piers, come from Ding's own table.
- **What the character knows**, learned in game and kept per character: the flight paths when a
  flight map opens (`TAXIMAP_OPENED`: `C_TaxiMap.GetAllTaxiNodes`, else the legacy taxi
  functions; each reachable node matched to its flight master within 150 yards; the map's
  coordinates are trusted only if its current node is the flight master next to the player,
  which is known in any case), the inn when the hearthstone is bound (`HEARTHSTONE_BOUND`) or
  where it lands (loading screen, or a jump of the position); a hearthstone bound elsewhere
  since (its name changed) is not used.
- **The arrow** follows the first leg that is not a walk: it points to the flight master with
  "Fly to Lakeshire, Redridge", to the dock with "Take the boat to Darkshore" (zeppelin, tram),
  or keeps the target with "Hearthstone to Goldshire" (the item button then offers the
  hearthstone). The window repeats it under the step. Once at a dock, the arrow waits for the
  far side ("on board") until the player gets there (5 minutes at most after leaving the dock).
  On a flight, the plan starts where it lands (`TakeTaxiNode`, watched with `hooksecurefunc`).
  A `go` step is still validated on its own point.
- The plan is made again when the target changes, the player moved 150 yards, or after 15 s.
- **Flight map**: when the plan flies the player, a Ding banner names the destination ("Fly to
  …") and a ring marks its node, both Ding frames on UIParent placed where the game's node button
  stands (only read): Ding never anchors to, shows, hides nor changes the game's flight map.

### Persistent objectives (`sticky`)

A step's `sticky` quests join a per-character set (`Ding.char.sticky`) once the step is
reached; while such a quest is in the log and not ready, its unfinished objectives are listed
under every following step (with the along-the-way rows, first, "Still to do · For “quest”",
whatever the distance; never twice, never under a step that names the quest), and their targets
are **low-priority arrow candidates** on the steps with quests (not on a trip: a `go` point
must stay the arrow's to be validated): such a point counts as twice its distance plus 300
yards. A quest turned in leaves the set.

### Section wrap-up

Past the section's `maxLevel` (and with a `next`), three rows under the step: "Next section:
…" (takes it up where the player is), "Turn in first (N steps), then the next section" (only
the turn-in steps of quests still in the log stay, then the guide chains; `Ding.char.wrapUp`)
and "Stay in this section" (remembered, `Ding.char.stay`). A click or A in focus mode.

### Next steps preview

"Next steps shown" (Appearance, 0 to 3, off by default): under the step's rows, the first line
(`Engine:Describe(step, true)`) of the next steps still to do, dimmed (state "preview").

### Minimap pins (`UI/MinimapPins.lua`)

On the minimap, with Ding's own textures: the arrow's target (an accent ring) and up to 5 of
the step's nearest spots (dots), or in a farming loop up to 12 of its stops, placed from the world positions with the minimap's zoom
(Classic yards per zoom level, indoors and out, `IsIndoors`) and its rotation
(`rotateMinimap`); the target farther than the minimap shows: an arrow on its rim. Hidden in
instances, with the guide window, or with "Pins on the minimap" off (Appearance). No world map
pins.

### Quest rewards (`Core/Rewards.lua`, `UI/Rewards.lua`)

With several rewards to choose from (`QUEST_COMPLETE`), Ding works out the best one: the best
**upgrade** for the class (each item's stats weighted for the class while leveling: primary
stats, stamina, armor, weapon damage per second for the hands or the ranged slot, wands
included; against what is equipped in that slot, the weaker ring or trinket, both hands for
a two-hander; only items the class can use, at least half a point better), else the item that
**sells for the most**. A banner names it and a ring marks its button in the game's quest
window (Ding's own frames, the window only read). With the option "Choose quest rewards"
(Automation tab, **off** by default, with automatic turn-in on), Ding takes it; Shift (LT)
held leaves the choice to the player. Items the client has not loaded yet are looked at again
when they arrive (`GET_ITEM_INFO_RECEIVED`, or a second later); nothing is taken meanwhile.

### Quest log cleanup

The Guide tab lists, under "Quest log cleanup", the quests of the log that neither the active
guide nor the guides after it ever use (prerequisites of their quests included), each with its
card ("Details", A or a click). When the log holds 16 quests or more, the window says how many
can go. The player abandons them **from the game's quest log**: abandoning needs the quest
selected in that log (`SelectQuestLogEntry` / `C_QuestLog.SetSelectedQuest`), which Ding never
calls (taint, `taint_test`).

### Level steps (guided grinding, `Core/Grind.lua`)

Yendi's feedback: the guide stopped on "reach level X" with nothing else to say. A level step
now shows, on its row:

- the **percent of the current level** as its counter, and under it the **experience left**
  to the step's level and **about how many kills** that makes. The experience of a kill is
  measured on the player's own last 30 kills (`PLAYER_XP_UPDATE` deltas), kept as a share of
  a monster of the player's level (`5 × level + 45`, Classic) so that they stay valid from one
  level to the next; without measures, the formula itself. The rested bonus is left out of the
  measure (a kill with rest left after it gave twice its experience), and it shortens the
  count: `kills = max(left - rested, left / 2) / experience per kill`. Experience within 1.5 s
  of a turn-in (either order) is the quest's, and a gain of more than three monsters of the
  player's level (a discovery) is not a kill;
- a row **"Kill <monster> · levels 3-4"**, the monster to farm, and the arrow on its spawns (a
  hunting area). Candidates: the monsters (killed or looted) of the quests of the log still to
  complete first (each kill counts twice), then those of the next 15 steps, then of the 15
  steps just done; never an elite or a boss, nor a monster of the player's side, nor grey (no
  experience), nor more than 2 levels above the player. The cost of each is the trip to its
  nearest spawn plus half the trip on to the guide's next place, plus the kills left (more of
  them when the monster gives less experience, Classic "zero difference"), riskier above the
  player's level. It is chosen again when the step, the level or the quest log changes, and
  every 15 s. With no monster to suggest, the arrow points to the guide's next place (reaching
  it does not validate the level step);
- the step passes by itself as soon as the level is reached, like before.

### Along the way (`Core/Along.lua`)

Under the current step, the window lists the unfinished objectives of the other quests of the
log whose targets (monsters, objects, item sources) are within 100 yards of the player: they
stay listed until the player is 160 yards away (no flicker), the objective is done or the
quest leaves the log. Three at most, the guide's next quests first, after the step's own rows;
the first one says "Along the way · For “quest”". Hovering, clicking (A in focus mode) works as
for the step's objectives. The objective the level step already farms is not repeated. Looked
at every 2 s while the window is shown, and on every quest log change.

  move around the minimap; can be hidden (Appearance, `/ding minimap`).

### Keyboard and mouse

Player feedback: without a gamepad, nothing could be confirmed (help and messages only showed
gamepad buttons). Every gamepad action therefore has an equivalent:

- **Click** = A (select, tick, confirm, bind); **right click** = Y (default value,
  unbind) or cancels a confirmation; **Esc** = B (closes the settings, cancels a
  capture or move mode).
- Confirmation: the button says "Click again to confirm". Binding conflict: "click to
  replace, right-click to cancel" (a click elsewhere also cancels). A capture takes a
  keyboard key just like a gamepad button.
- Move mode: drag the frame with the mouse; "Save", "Cancel" and "Reset" buttons on the
  plate, Enter saves, Esc cancels.
- **The help bar is clickable** (settings and the move mode plate): a click on
  "A Select", "B Back", "Y Reset" or "LB/RB Tabs" does what the button does.
  These hints look like buttons (background, border, lighter on hover); the D-pad hint and
  the mouse help text, which cannot be clicked, stay plain text. Yendi's feedback: with no
  gamepad plugged in, you could neither confirm nor cancel, since A and B were only pictures.
- "Gamepad" means **enabled and plugged in** (`Gamepad:Active`: `C_GamePad.IsEnabled` or
  the `GamePadEnable` variable, and at least one device in `C_GamePad.GetAllDeviceIDs`),
  checked again on every `GAME_PAD_CONNECTED` / `GAME_PAD_DISCONNECTED`. Without a gamepad,
  the help bar and these messages talk mouse and keyboard ("Click: change · Right-click:
  default · Esc: close"), with no glyph; with a gamepad, nothing changes. `mouse_test`
  checks it.

### Gamepad

- Game bindings: next / previous step, show the guide, minimize the guide, open the
  settings, use the quest item, target the arrow's NPC or monster, browse the guide (focus
  mode), skip the step, go back to a skipped step, nearby services, the arrow on the step's next target. They work in combat,
  except opening the settings, focus mode and the services list.
- No window captures a button permanently: the guide window stays displayed without
  taking anything away from the game.
- Focus mode of the guide window: the D-pad moves through the lines, A points the arrow at
  the line (or uses the item on the item's line, equips a gear upgrade), X shows its quest's
  card, Left ignores the gear upgrade under focus, LB / RB change step, Y minimizes, B exits.
  On a talent suggestion, A twice learns the talent. Right, on a row with a quest, finds that
  quest in the guide; Left drops the offer.
  Only these buttons are taken; the mode stops in combat.
- Settings window: temporary bindings (`SetOverrideBindingClick`) set when it opens
  and removed when it closes. A confirms, B closes or cancels, Y resets to default or clears,
  LB / RB change tab, the D-pad selects and adjusts (repeats when held). The window
  closes on entering combat.
- Move mode for the guide window, the arrow and the item button with the D-pad (steps
  of 5, 1 with LB, 20 with RB, the mouse works too), A saves, B cancels, Y restores the
  original position.
- Binding a button from the Keybinds tab, with conflict detection; buttons are shown as
  Xbox chips (A, LB, LT+Right) or PlayStation chips (symbols).
- First launch: the window opens on the bindings so the player can bind "Open Ding
  settings".

### API compatibility

The Forever client shares Retail's project ID but ships the Classic API, and some old
functions exist but fail. Ding goes through `Core/Compat.lua`, which prefers
`C_QuestLog.*` and `C_Map.*`, protects calls (`pcall`) and falls back to the legacy
functions when needed.

## 4. Timing (for the optimizer)

For each step finished **during the session**, Ding records in `DingDB.timings`:
duration, and level and XP at the start and at the end (positions 1 to 5, then the date: the
only fields of the older samples), plus `map` (UiMapID where the step ended), `deaths`,
`kills` and `killXP` (the kills during the step and their experience), `levelStep` (a
`level` step) and `step`, the step's signature (`"a456,458 c456 t457 l12 g"`) to find it
again once a guide is regenerated and its steps move. Steps caught up automatically at
login are not counted, nor steps longer than an hour (four for a level step: the player was
away). The last 20 measurements per step are kept.

The file `WTF/Account/<account>/SavedVariables/Ding.lua` then serves as input to the
optimizer, to replace its estimates with real times.

## 5. Optimizer (out of game)

`tools/draft_guide.lua` writes the guides of a route (`tools/routes/*.lua`); the details are
in `tools/README.md` (§6).

Input: the QuestieDB Forever export (quests, NPCs, objects, map geometry, drop rates,
quest XP) and the route (zones, level brackets, forced or excluded quests, notes).
Output: a guide file in the format above, and its translation.

1. **Quest graph** (`tools/route_data.lua`): accept (giver, or starting item dropped
   by the monsters of another quest), objectives (densest spawn clusters, each with the
   level of its own monsters, number of targets read from the quest text, drop rates) and
   turn-in of each quest, prerequisites, chains, levels, exclusive quests, XP (QuestieDB's
   `QuestXP` table).
2. **Time model** (`tools/route_model.lua`, `PARAMS` table; travel in
   `tools/route_travel.lua`): travel (world distance × detours / speed, mount at level 40,
   flight paths between the faction's flight masters, boats, zeppelins and the tram,
   hearthstone to the bound inn once an hour, the binding itself chosen by the
   optimizer), time per objective (number of targets, spawn density, drop rate,
   respawns), monster XP (Classic formula). Parameters grouped together for
   **recalibration with real measurements** (`DingDB.timings`, §4): to do.
3. **Solving** (`tools/route_solver.lua`): a tour with pickups and deliveries
   (*pickup and delivery*), under constraints of prerequisites, exclusive quests, level
   (quest XP in full, monster XP with a 90% safety margin), gray quests and a **limited
   quest log** (18 quests, a margin below 20). **A quest at most 2 levels above the
   player, its monsters at most 1** (Yendi's rule, 12/10/2026; the required level is never
   above): the quest waits for the level, in the guide or in the next one, behind a `level`
   step when the stop pays off (a quest that a later guide needs: an hour of stops per
   guide at most). Start:
   the nearest-neighbor tour, then simulated annealing (moves, swaps, 2-opt, Or-opt,
   quest removal and reinsertion, ruin and recreate), fixed seed.
   Objective function: **XP per hour**, expressed as the time needed to reach the guide's
   maximum level (XP from quests and killed monsters, reduced XP for quests that are too
   easy, missing XP filled in by grinding): a quest is kept if it pays off faster
   than grinding, detour included; a grinding stop counts as lost time plus 15 minutes
   (a wall in the guide).
   **Level windows**: `tools/fit_windows.lua` cuts each guide's window from the level the
   previous one reaches, so that no guide ends with a `level` step just to reach the next
   one's minimum (see `tools/README.md` §6).
   **Leveling guides** (Ding! - Leveling): `tools/write_leveling.lua` writes them from the Leveling
   routes (`tools/routes/leveling/<faction>.lua`: the route's
   order, shortcuts and race and class steps are kept as written; Forever
   changes it as little as possible (a quest missing, closed or already done is left out for
   those concerned, a missing prerequisite on the same map is done first, a quest waits for
   its prerequisite's turn-in), and Forever's own quests are inserted where the detour is
   smallest, within the +2 / +1 caps (only they follow them). See `tools/README.md` §7.
   The zone guides' optimizer (`draft_guide.lua`) also builds guides over several zones
   (a level bracket over a pool of zones, the order across them optimized), for the
   Skyborne starts (one per side).
   **Steps behind an option**, each on a step of its own: `sethearth` / `hearth` (where the
   optimizer binds and uses the hearthstone), `deathskip = true` with its `text`,
   `dungeon = "<dungeon name>"` and `elite = true` on every step of such a quest (accept,
   objectives, turn-in). Skipped, the guide stays valid: shortcuts are only shortcuts, and no
   other step needs a dungeon or elite quest (`tools/check_guides.lua` checks it). A quest
   done in a dungeon (`route_data.lua` `questDungeon`) is never part of the tour.
4. **Export** of the guide, then human review (elite quests, contested PvP zones…).
   `--report` shows, per guide, distance, estimated time, XP and XP/h before and after
   optimization, and the reason for each removed quest.
